# qBittorrent compatibility

- Before changing settings or API calls, read `docs/version-compatibility.md` and `docs/qbittorrent-schema-audit-ru.md`.
- Use official qBittorrent Wiki, tagged qBittorrent source, and libtorrent documentation. Wiki examples can be outdated; verify keys/types/units/enums against the target release's controller and session implementation. Preset heuristics are not official recommendations.
- Never introduce direct INI/CONF writes. Use the validated Web API, save original values before mutation, and verify apply/rollback by readback. Keep credentials out of persisted data.
- For a new supported minor branch, audit its release tag, update the version gate and `scripts/check_qbittorrent_schema.py`, add version/contract regressions, and update the compatibility documents. Do not automatically admit future versions.
- Run `python -m pytest tests/ -q` and `python scripts/check_qbittorrent_schema.py`. The second command reads public upstream sources and needs network access. Neither command should change a user's real qBittorrent.

# CI/CD and build contract

- Read `docs/build-layout-design.md` before changing build scripts, artifact paths, cleanup rules or workflows. Keep local builds and CI on the same entry point: `scripts/build.py`. Do not add independent PyInstaller commands or alternate output directories.
- `.github/workflows/tests.yml` runs on pushes to any branch, pull requests and manual dispatch. It uses `windows-latest`, Python 3.11 and uv; installs locked development dependencies, runs regression tests and checks the official tagged qBittorrent API contract. It has read-only repository permissions and does not publish releases.
- `.github/workflows/release.yml` runs on pushed `v*` tags. It installs dependencies, runs tests and the upstream API contract check, builds through `scripts/build.py`, then uploads the EXE and manifest to a GitHub Release with generated release notes. Only this workflow needs `contents: write`; use its provided `GITHUB_TOKEN`, never a committed token.
- Use `uv sync --locked --extra dev` and `uv run --locked --extra dev ...` for reproducible CI checks. Update `uv.lock` locally when dependencies change; do not regenerate it as part of CI.
- Keep generated files inside the designated directories: `UV_CACHE_DIR=.cache/uv`, `UV_PROJECT_ENVIRONMENT=.cache/venv`, `PYTHONPYCACHEPREFIX=.cache/pycache`. Pytest uses `.cache/tests` and `.cache/pytest` through `pyproject.toml`.
- Required verification commands are `uv run --locked --extra dev python -m pytest tests/ -q` and `uv run --locked --extra dev python scripts/check_qbittorrent_schema.py`. GUI tests require a graphical Windows session and Tcl/Tk; the upstream contract check requires network access. Do not skip a failed check to publish an EXE.
- Local full build: `build.bat`. Build from a prepared environment or in CI: `uv run --locked --extra dev python scripts/build.py`. The build module compiles into `.cache/staging`, uses `.cache/pyinstaller` for intermediate files, and checks the packaged `--check` and `--smoke-test` before publishing locally.
- The only current executable is `artifacts/release/qFrey-Tuner.exe`; its manifest is `artifacts/release/build.json` (version, UTC build time and SHA-256). GitHub Release uploads exactly these two files. `Run.bat` selects this EXE, never an archived build. Do not compile EXEs into the repository root, `outputs`, `dist` or `distribution`.
- Before replacing the current EXE, preserve it and its manifest in `artifacts/archive/builds/<UTC>/`. Keep older migrated builds in `artifacts/archive/legacy/`. Do not delete old EXEs or archives without a separate user request; never clear `state` or experiment backups during builds or cache cleanup. A locked/running EXE must fail safely rather than being forcibly terminated or deleted.
- The version source is `pyproject.toml`; the build does not bump it. Before publishing a release tag, verify that `v<version>` matches the project version, the intended commit passed checks, and the manifest checksum matches the EXE. Creating/pushing release tags publishes externally: do it only when the user requests a release. A branch push alone does not create a release.
- When changing the pipeline, validate the affected workflow, local build entry point, output paths and archive behavior together. Report which checks actually ran and any blocked checks; do not describe local success as a successful GitHub Actions run without inspecting that run.
