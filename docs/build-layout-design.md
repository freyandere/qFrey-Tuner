# Design doc: сборка и размещение файлов qFrey-Tuner

Дата: 2026-10-05. Решение: принято для локальной сборки и ручной публикации GitHub Release.

## Проблема

Разные команды сборки создавали EXE в dist, outputs и вложенных папках предпросмотра. В корне накапливались одноразовые скрипты, каталоги pytest и зависимости. Номер версии не позволял определить, какой из нескольких одинаково названных EXE актуален.

## Постоянная структура

| Путь от корня проекта | Назначение | Политика хранения |
|---|---|---|
| artifacts/release/qFrey-Tuner.exe | Единственный актуальный EXE | Заменяется только после успешной сборки и проверки запуска |
| artifacts/release/build.json | Версия, время сборки UTC и SHA-256 EXE | Обновляется вместе с актуальной сборкой |
| artifacts/release/state/ | Данные приложения, резервные копии настроек, журнал | Не очищается сборкой или уборкой кэша |
| artifacts/archive/legacy/ | Ранее созданные EXE, с сохранением исходных относительных путей | Не удалять без отдельного запроса пользователя |
| artifacts/archive/builds/<UTC>/ | Предыдущая актуальная сборка и её manifest | Сохранять перед заменой актуального EXE |
| artifacts/session-backups/legacy/ | Данные state из старых мест запуска | Сохранять, не объединять файлы с одинаковыми именами |
| artifacts/reports/ | Локальные отчёты проверок и уборки | Можно архивировать; не смешивать со сборками |
| .cache/staging/ | EXE-кандидат до проверки | Временная область; успешный кандидат переносится в release |
| .cache/pyinstaller/ | Объектные файлы, анализ импортов, промежуточные файлы PyInstaller | Восстанавливаемый кэш |
| .cache/tests/, .cache/pytest/ | Временные данные и кэш тестов | Восстанавливаемый кэш; pytest очищает только свою область |
| .cache/pycache/ | Python bytecode при запуске через скрипты проекта | Восстанавливаемый кэш |
| .cache/uv/, .cache/venv/ | Кэш зависимостей и окружение uv | Восстанавливаемые из uv.lock |
| .cache/tools/, .cache/build-deps/ | Локальные инструменты текущей среды Codex | Вспомогательные файлы этой машины; не требуются установленному EXE |
| docs/ | Design docs и документация | Версионировать в Git |

artifacts и .cache исключены из Git. EXE не коммитятся. GitHub Release получает artifacts/release/qFrey-Tuner.exe и build.json. Версия релиза определяется тегом; версия окна — pyproject.toml. Новые каталоги outputs, dist, distribution и build в корне не являются разрешёнными местами результата.

## Единственный маршрут сборки

Локально: `build.bat`. При ручной сборке из подготовленного Python-окружения: `python scripts/build.py`. Обе команды используют один сборочный модуль; добавлять отдельные команды PyInstaller в другие скрипты не нужно.

build.bat устанавливает зависимости из uv.lock, выполняет тесты и проверку окна, затем вызывает scripts/build.py. Сборочный модуль использует абсолютные пути относительно проекта, собирает кандидат в .cache/staging, проверяет `--check` и `--smoke-test`, архивирует прежний актуальный EXE и публикует новый. PyInstaller spec отклоняет произвольные пути результата и промежуточных файлов. Не запускайте `pyinstaller qFrey-Tuner.spec` напрямую: используйте общий модуль.

Run.bat запускает только artifacts/release/qFrey-Tuner.exe либо исходники, если EXE ещё не собран. Архивные EXE автоматически не выбираются. Сборка не повышает версию самостоятельно.

Ошибка компиляции или проверки запуска сохраняет текущий release. Заблокированный запущенным приложением EXE не удаляется: публикация завершается ошибкой, пользователь закрывает окно и повторяет сборку. Архивы не очищаются автоматически.

## Уборка существующих файлов

Сначала скопировать каждый старый EXE в artifacts/archive/legacy/<исходный путь> и проверить SHA-256. После проверки можно перенести его исходное размещение; исполняемые версии не удалять. Запущенные или заблокированные файлы оставить до закрытия приложения.

Перед удалением старых каталогов сохранить все их папки state в artifacts/session-backups/legacy/<исходный путь>/state. Актуальную outputs/state перенести также в artifacts/release/state, чтобы смена пути EXE не потеряла текущие настройки приложения. Не перезаписывать существующий state и не сливать резервные копии автоматически.

Существующие build/dist/distribution/outputs/work перенести целиком в artifacts/archive/legacy: помимо EXE там могут быть полезные отчёты и другие файлы. Без отдельного решения их содержимое не удалять. Удаление ограничить старыми .ux_* скриптами, .ux-tests-* каталогами, .test-deps, __pycache__ и .pytest_cache. Зависимости для текущей среды перенести в .cache/build-deps, локальный uv — в .cache/tools/uv. .git, исходники, текущие незакоммиченные изменения, .agent, .vscode, .venv, Info и материалы пользователя в 0.Inbox/changelogs не являются мусором и в эту уборку не входят.

Проверять разрешённые абсолютные пути перед рекурсивным удалением. Не следовать junction/symlink наружу. Не удалять скачанные ISO, профили qBittorrent, настройки клиента или данные экспериментов. Состав перенесённых файлов записать в artifacts/reports/cleanup.json.

## Проверка решения

Тест публикации подтверждает сохранение старого EXE и manifest перед заменой. Полный набор тестов и проверки собранного EXE должны пройти. В корне не должно появляться новых EXE или временных каталогов сборки; постоянный результат и архив должны соответствовать таблице выше. После уборки проверить количество и SHA-256 сохранённых старых EXE.

## Публикация релиза

GitHub Actions не используются. До публикации локально выполнить тесты, проверку официального API и сборку через build.bat. Затем загрузить актуальные qFrey-Tuner.exe и build.json в GitHub Release с тегом v<версия из pyproject.toml>, указывающим на проверенный коммит ветки windows. Проверить SHA-256 загруженного EXE, имена и размеры файлов. Исходники и документация идут в Git; EXE, state, архивы и кэш остаются исключёнными. Секреты авторизации не сохранять в проекте.
