## Решение

Переход оправдан прежде всего ради интерфейса, удобства экспериментов и интеграции с Windows. Он не является способом автоматически ускорить qBittorrent. Переносить backend по проверяемым контрактам, frontend переписать полностью; сначала сохранить поведение, затем расширять свободу пользователя.

Минимальная целевая архитектура: одно WPF-приложение на .NET 10 LTS с одним WebView2, локальный frontend на TypeScript и Tailwind, обмен ограниченными JSON-командами. Backend работает внутри процесса приложения. Отдельный ASP.NET-сервер, localhost-порт, Windows Service, Electron, Python-процесс в поставке и база данных не нужны.

Frontend первого этапа: TypeScript + Vite + Tailwind, обычные DOM-компоненты и один объект состояния представления. Tailwind отвечает за оформление, а не за состояние или доступность. Не создавать собственный UI-фреймворк; необходимость React рассмотреть только если прототип покажет существенное усложнение повторяемых интерактивных компонентов.

.NET 10 имеет статус LTS в [официальной политике поддержки](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core). Конкретные версии SDK, NuGet и npm зависимостей зафиксировать при старте ветки, не привязывать план к плавающим latest.

## Backend и граница с frontend

Начать с трёх проектов: Core, Desktop и Tests; frontend держать отдельно внутри репозитория. В Core — расчёты, API и эксперимент, в Desktop — WebView2, диалоги и Windows-интеграция. Не добавлять repository/service/factory слои без реальной потребности.

Frontend отправляет конкретные команды: Connect, Preview, StartMeasurement, CancelMeasurement, ApplyPlan, Rollback, RestoreBackup и операции управляемой загрузки. Ответы содержат requestId, operationId, revision, результат или структурированную ошибку; события — состояние и прогресс. Это ограниченный протокол приложения, не произвольный HTTP/shell/file proxy.

Backend хранит авторитетное состояние и возвращает допустимые действия с причинами запрета. Нельзя разрешить Apply только потому, что кнопка активна: C# повторно проверяет цель, ревизию плана, baseline и текущие preferences. Отложенный ответ от старого подключения не должен обновлять новую сессию.

Одновременно выполняется одна операция, изменяющая эксперимент или создающая измерительную нагрузку. Чтение уже полученного состояния, справки и результатов доступно всегда. CancellationToken прерывает ожидания и HTTP-чтение; отмена после отправки мутации не означает откат. При неопределённом результате записи сохраняется backup, выполняется readback/recovery, UI честно показывает неизвестное или частичное применение.

Состояние соединения, фаза эксперимента и выполняемая операция — отдельные поля, а не все комбинации одного огромного enum. Фазы включают отсутствие baseline, baseline ready, plan ready, application unverified, applied verified, measured и rollback required. Разрешения определяются короткими проверяемыми правилами, без библиотеки state machine.

Локальные HTML/CSS/JS поставляются с приложением, без CDN. Использовать контролируемый origin и поддерживаемую загрузку [локального контента](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/working-with-local-content). Проверять origin, типы, размеры и поля сообщений; блокировать внешнюю навигацию внутри привилегированного WebView, внешние ссылки открывать в браузере. Не экспортировать универсальные host objects. Это соответствует [рекомендациям безопасности WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security).

Credentials после ввода передаются backend и очищаются из формы; cookies и ключи не возвращаются в UI-снимках, не сохраняются в localStorage, логах или backup. TypeScript-типы не заменяют runtime-валидацию JSON в C#.

## Пользовательский сценарий

Сохранить понятную последовательность: подключение → проверка условий → исходный замер → просмотр плана → применение → повторный замер → решение. Вместо семи равноправных вкладок предложить четыре раздела: «Подключение», «Условия», «Эксперимент», «Результаты». В «Условиях» объединить сеть, железо и цели; внутри эксперимента показать последовательные этапы.

Постоянная строка состояния показывает endpoint, проверенные версии, текущую операцию и факт изменения настроек. Активный тест не уводит пользователя насильно на другой экран. Контекстная панель отвечает на три вопроса: что происходит, почему действие недоступно, что сделать дальше.

Для каждого параметра: текущее → предложенное, единица измерения, причина рекомендации, применимость к сборке. Разделять «измерено», «введено вручную», «определено локально» и «эвристика». При подключении к NAS/seedbox характеристики Windows-компьютера не выдавать за характеристики удалённого сервера.

Ошибки размещать рядом с действием. Например: «Настройки применены и проверены. Повторный замер не завершён: тестовая загрузка закончилась. Повторить тест / Откатить изменения». Отдельно показывать «резервная копия сохранена, применение не подтверждено». Эти различия уже есть в Python и должны сохраниться.

Расширенная свобода после паритета: выбор отдельных рекомендаций, допустимое ручное значение, сохранённые наборы входных данных и сравнение истории. Любая правка формирует новый проверенный план; зависимости параметров валидируются, stale preview неприменим. Изменения черновика во время замера не меняют снимок текущего эксперимента. Expert mode не отменяет backup/readback/version gate.

Guidance не должен усиливать сомнительные обещания текущих текстов calculator.py: «обход DPI», «Kill Switch» и «оптимальные настройки» нельзя показывать как доказанные результаты. Числа сначала переносить для паритета; формулировки уточнить как гипотезы/ограничения. Отчёт уже прямо перечисляет неизмеренные CPU/RAM, disk latency, port reachability и VPN leak protection — сохранить это разграничение.

Для визуального стиля: спокойная светлая/тёмная тема, единая шкала отступов, небольшое число акцентных цветов, компактные карточки и полноценная таблица diff. Цвет не единственный носитель статуса. Проверить клавиатуру, фокус, screen reader, reduced motion и масштабы 100/125/150/200%. Для текущих коротких графиков достаточно SVG, сложная chart-библиотека пока не нужна.

## Этапы и критерии завершения

1. **Зафиксировать эталон.** Создать ветку от проверенного commit windows, записать SHA. Запустить текущие тесты и upstream checker. Сохранить обезличенные входы/ожидаемые результаты калькулятора, API payloads, метрики и старые cycle/workload JSON. Случайный порт проверять фиксированным тестовым значением, не сравнением разных генераторов случайных чисел. Снять baseline времени запуска, RAM/CPU и действий пользователя.
2. **Проверить оболочку и упаковку.** WPF + один WebView2, локальная страница, одна типизированная команда и прогресс/отмена на имитации. Проверить запуск без установленного .NET, отсутствие WebView2, DPI, offline UI и размещение runtime cache. Критерий: выбранный формат поставки работоспособен с нынешним контрактом EXE + manifest.
3. **Перенести чтение и расчёты.** Модели, калькулятор, авторизация, version gate, live schema, preview, hardware detection. Критерий: C# и Python дают одинаковые числовые результаты и API-планы на выбранной матрице; неподдерживаемые версии и типы отклоняются. Реальные настройки ещё не изменяются.
4. **Перенести безопасный эксперимент.** Durable backup до записи, apply/readback, частичная ошибка, rollback, восстановление старого JSON, владение workload, парсер метаданных, замер и метрики. Критерий: портированные контрактные сценарии проходят, включая сбой сохранения, disconnect после записи, preference drift, отмену и запрет удаления чужого торрента.
5. **Собрать полный frontend.** Четыре раздела, diff, графики, объяснения, просмотр во время работы. Критерий: полный цикл в тестовой среде, двойной клик не запускает дублирующую мутацию, stale события игнорируются, все текущие функции имеют место в новом UI. Проверить сценарии и в браузерном тесте, и внутри настоящего WebView2.
6. **Добавить расширенный режим.** Выбор изменений и ручные значения с backend-валидацией, история экспериментов. Критерий: пользователь понимает область применения и может восстановиться после прерывания; защита текущего цикла не ослаблена.
7. **Проверить и подготовить выпуск.** Windows QA, отдельный тестовый профиль qBittorrent, apply/readback/rollback и штатный restart, сравнение ресурсов, сборка и packaged checks. Только после этого кандидат может заменить текущий локальный EXE; push/tag/release — отдельное явно запрошенное действие.

Ориентир для одного разработчика, знакомого с обоими стеками: 1–2 дня на эталон, 2–4 на shell/packaging, 3–5 на read-only backend, 5–8 на безопасный цикл, 4–7 на frontend, 3–5 на расширенный режим, 3–5 на проверку и выпуск. Всего примерно 21–36 рабочих дней; это инженерная оценка, не обещание срока. После этапа 2 пересмотреть её по фактическим сложностям Windows-интеграции и упаковки.

## Совместимость и сборка

Не расширять поддержку qBittorrent при смене языка. Сохранить текущий gate: stable 4.6.x/5.0.x/5.1.x/5.2.x; API stable 2.8+ внутри v2; libtorrent stable 1.x/2.x. Ключи, типы, единицы, enums и исключения LT2 переносить по version-compatibility.md и qbittorrent-schema-audit-ru.md. Любое новое поле/ветка требует отдельной сверки tagged source. INI/CONF остаются только источником подсказок, не каналом записи.

Python schema checker в период миграции сохранить как инструмент разработки. Дополнить проверкой фактического набора C# preference keys/payloads: успех проверки только старого Python-адаптера не доказывает совместимость новой реализации. Общие тестовые данные допустимы; runtime-зависимость нового приложения от Python не нужна.

Сохранить `scripts/build.py` единственной точкой упаковки и `build.bat` полным локальным маршрутом. В ветке изменить внутренние шаги сборочного модуля для TS и .NET после обновления build-layout-design.md. Версию по-прежнему брать из pyproject.toml и передавать в .NET/frontend; не вводить независимые номера в package.json/csproj.

Frontend bundle, npm/NuGet cache, .NET obj/bin и промежуточные публикации направлять внутрь .cache; кандидат — в .cache/staging. Не допускать Vite dist или dotnet bin/obj как новых выходных каталогов корня. Зафиксировать Node/.NET SDK и lock-файлы. Сохранить существующие UV_CACHE_DIR, UV_PROJECT_ENVIRONMENT, PYTHONPYCACHEPREFIX для Python-инструментов.

Целевая гипотеза поставки — self-contained Windows x64 EXE с упакованными web assets и Evergreen WebView2 Runtime как внешней предпосылкой. Single-file и загрузку native WebView2 loader обязательно подтвердить этапом 2; не выдавать их за уже решённые. При отсутствии runtime показать понятный путь установки, без скрытого скачивания. [Microsoft требует наличия WebView2 Runtime](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution); установленный браузер Edge не заменяет контракт runtime. Fully offline поставка на чистый ПК потребует отдельно пересмотреть способ доставки runtime и текущие два release assets.

После успешных packaged `--check` и `--smoke-test` публиковать локально только artifacts/release/qFrey-Tuner.exe и build.json, с предварительным архивированием текущей пары. Сохранить Run.bat, state, все архивы, запрет force kill и безопасный отказ при locked EXE. Profile WebView2 держать в LocalAppData отдельно от пользовательских backup. Старые JSON импортировать с проверкой версии/типов; перед миграцией сохранять исходник, не переписывать legacy backup на месте.

## Как доказать улучшения

На одном ПК и одинаковой версии runtime выполнить серию холодных и тёплых запусков обеих версий, сравнить медиану и p95. Измерять запуск до интерактивного UI, переходы экранов, CPU в простое/замере и суммарный private working set приложения вместе с дочерними WebView2-процессами. Не сравнивать только память процесса C# с полной памятью Python.

Предлагаемые цели прототипа, не полученные результаты: реакция обычного UI-действия p95 <100 мс, доступная навигация при долгом API-запросе, отсутствие регрессии запуска более 20% относительно эталона. Память оценить по замерам и установить бюджет после этапа 2. Числа измерительного протокола не сокращать ради красивого времени выполнения: текущие 10 секунд прогрева и 60 отсчётов — часть методики.

Для guidance дать нескольким пользователям без подсказок выполнить подключение, понять причину блокировки, просмотреть diff, обработать неудачный повторный тест и восстановить настройки. Сравнить время, ошибочные действия и обращения за помощью с текущим UI. Красивый экран без улучшения этих сценариев не считается выигрышем.

При реализации обязательны `uv run --locked --extra dev python -m pytest tests/ -q` и `uv run --locked --extra dev python scripts/check_qbittorrent_schema.py`, а также C#/frontend проверки и packaged checks. GUI проверяется на Windows; upstream checker требует сеть. Все автоматические мутации — только в mock API, живой end-to-end — в отдельном тестовом профиле.
